# Community Participation

OpenReady is a free, non-commercial open-source project. People can contribute through documentation, accessibility review, testing, issue reporting, design feedback, code, triage, and constructive community support.

This document explains how a person can begin with one focused contribution, how project labels are used, and how contributions may be recognized.

## Participation pathway

A typical path is:

1. Use OpenReady or read its documentation.
2. Report one clear problem, question, or improvement.
3. Complete one small, reviewed contribution.
4. Return for another focused task when capacity allows.
5. Help with review, testing, documentation, or triage after learning the project.
6. Take on trusted responsibilities only through the role and permission process in [GOVERNANCE.md](GOVERNANCE.md).

There is no requirement to move through every step. A single useful report, accessibility observation, documentation correction, or test session is a complete contribution.

## First contribution pathway

For a first contribution:

1. Read [CONTRIBUTING.md](CONTRIBUTING.md), the [Code of Conduct](CODE_OF_CONDUCT.md), and the issue description.
2. Choose an open issue labeled `good first issue`, or ask in [GitHub Discussions](https://github.com/Jpelotea/openready/discussions) whether a small task is still available.
3. Comment on the issue before beginning substantial work so duplicated effort can be avoided.
4. Keep the change limited to the issue's acceptance criteria.
5. Run the verification steps listed in the issue or contribution guide.
6. Open a pull request that explains what changed, why, and how it was checked.
7. Respond to review comments when practical. A request for revision is part of normal collaboration, not a judgment about the contributor.

A contributor does not need to be an expert developer. Tasks may involve wording, links, test evidence, accessibility observations, screenshots, issue reproduction, or code.

## `good first issue`

The `good first issue` label is reserved for tasks that:

- have one small and understandable outcome
- identify the relevant files or interface area
- include clear acceptance criteria
- include practical verification steps
- avoid confidential information and sensitive security work
- do not require repository permissions
- can normally be completed without prior OpenReady knowledge
- are small enough for focused review

The label should not be used for broad redesigns, security incident work, governance disputes, release management, or accessibility testing that requires specialist assistive technology or unavailable hardware.

A labeled issue may be reassigned, narrowed, or closed when the work is completed, duplicated, no longer appropriate, or beyond current maintainer capacity.

## `help wanted`

The `help wanted` label identifies a scoped task where community participation would be useful. It may require specific experience, equipment, or deeper project knowledge.

Examples include:

- desktop or mobile screen-reader testing
- physical-device testing
- browser zoom and forced-colors review
- reviewing a complex import or compatibility change
- documenting an unfamiliar platform behavior

A `help wanted` issue should still describe the expected evidence, completion criteria, and maintainer review route. The label does not promise immediate support, assignment, acceptance, or a release date.

## Contribution types

OpenReady recognizes:

- **Documentation:** clearer explanations, corrected links, examples, templates, release notes, and policy improvements
- **Accessibility:** barrier reports, keyboard testing, screen-reader testing, zoom and reflow review, contrast review, and accessible design recommendations
- **Testing:** reproducible bug reports, browser checks, device checks, regression tests, and verification evidence
- **Issue reporting and triage:** focused reports, duplicate identification, reproduction confirmation, and scope clarification
- **Design:** interface feedback, information architecture, responsive behavior, and understandable interaction patterns
- **Code:** safe fixes, features, validation, performance improvements, and maintainable refactoring
- **Community support:** respectful answers that point people to project documentation without impersonating maintainers or promising outcomes

Contribution value is not ranked by whether it changes code.

## Recognition

Release notes may recognize contributors by GitHub username and contribution type, for example:

- Documentation: `@username`
- Accessibility testing: `@username`
- Bug report and reproduction: `@username`
- Code or test contribution: `@username`

Recognition should:

- describe the contribution accurately
- include non-code contributions where relevant
- avoid ranking people by volume
- avoid publishing private names or details without consent
- avoid implying employment, payment, endorsement, or a maintainer role
- be corrected when attribution is incomplete or inaccurate

A contributor may ask not to be named publicly.

## Review and response expectations

OpenReady is maintained on a best-effort basis. The response targets in [SUPPORT.md](SUPPORT.md) are planning expectations, not service-level guarantees.

Maintainers and contributors may pause, reduce scope, or decline work to protect project quality and sustainable participation. Metrics must not be used to shame contributors, create activity quotas, or require constant availability.

## Privacy and safety

Do not place credentials, exploit details, confidential reports, medical information, private personal information, or another person's identifying data in public issues or pull requests.

Use:

- [SECURITY.md](SECURITY.md) for sensitive vulnerabilities
- [CODE_OF_CONDUCT.md](CODE_OF_CONDUCT.md) for private conduct reports
- [ACCESSIBILITY.md](ACCESSIBILITY.md) for accessibility reporting guidance

OpenReady does not add website analytics or transmit checklist, project-profile, notes, or starter-material content to a project server.

## Conduct

All participation must follow the [Code of Conduct](CODE_OF_CONDUCT.md). Respectful disagreement, clarification, and review are welcome. Harassment, retaliation, pressure for immediate unpaid work, or misrepresentation of project authority is not.
